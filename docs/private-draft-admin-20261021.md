# 后台私人草稿整合说明（第三批，PR #45）

> 本文说明的是 **PR #45 依赖 PR #44** 的开发版本，尚未进入正式站点。前台页面、布局、组件、样式、文章渲染保持不变。

## 功能范围

- 后台文章列表同时展示公开 GitHub 文章及独立 KV 私人草稿，并明确标明两种草稿的区别。
- “保存草稿”不再向公开 GitHub 写入，而是向 **FIREFLY_PRIVATE_DRAFTS** KV 命名空间写入；如果 KV 未配置或请求失败，则停止并保留编辑器原文，不会自动退回公开仓库。
- 从当前已经在公开仓库的文章创建私人草稿时，只创建独立副本。**旧公开文件、Git 历史和其他缓存不会自动删除**。
- 支持选择单篇私人草稿、导出本地 `.md` / `.mdx` 备份以及导入同名冲突拒绝的备份文件。
- 私人草稿在发布到公开仓库之前必须人工确认；密码和未知元信息存在时自动阻止发布；成功后私人备份仍然保留。
- 如 GitHub 文章 API 暂时不可用，私人 KV 草稿依然可以独立加载。

## 部署前检查

1. 保持 PR #43（管理员密码轮换）与 PR #44（私人草稿 KV）独立验收，避免不经测试直接合并多个 PR。
2. 先创建专用私人草稿 KV 命名空间，配置 GitHub Actions Variable `FIREFLY_PRIVATE_DRAFTS_NAMESPACE_ID`，将 Worker 绑定名称设为 `FIREFLY_PRIVATE_DRAFTS`。不要与会话 KV 复用。
3. 在预览 Worker 登录后，用**虚构测试文章**完成创建、读取、更新、删除、导出与导入；验证无会话 API 返回 401、未绑定返回 503。
4. 用复杂 MDX 测试文件验证往返保真性：从私人 KV 编辑保存 -> 重新打开 -> 导出 -> 与原文件比较正文和保留语法。
5. 发布前确认正文允许公开、图片和外链允许公开。发布后检查 GitHub Commit、Cloudflare 真实构建与正式文章地址。
6. 同时打开两个浏览器编辑同一草稿，确认旧版本能返回 409；**这只是尽力检测，不是并发事务锁**。
7. KV 中真实数据必须有独立、经过恢复演练的备份。当前界面的**手动导出不是自动备份、也不是删除回收站**。

## 边界与注意事项

- 现有 GitHub 草稿不会自动迁移或消除旧历史；只能通过人工审查后选择“创建私人副本”。
- 当前私人草稿 API 和编辑器只为单人顺序编辑设计；Cloudflare KV 的最终一致性可能造成短期内列表延迟，**不要在多个设备上同时保存同一篇**。
- 管理员选择 AI 写作或润色时，文章可能发送给当前配置的第三方 AI 服务商，私人资料应避免未经确认上传。
- 插入的图片如果已经托管在公开图床上，正文转为私人草稿不会自动给图片加访问控制。
- 用户选择“私人草稿 -> 发布”是明确公开操作：GitHub 是公开仓库，网页密码不能阻止源码被读取。
- 仅创建 PR 并通过自动检查不等于完成真实 KV 联调，真实生产连接必须独立验收。

## 验收任务

| 项目 | 期望 |
| --- | --- |
| 前台视觉回归 | 不变 |
| 无 KV 绑定 | 后台提示不可用；草稿不提交公开 GitHub |
| 新建、编辑私人草稿 | KV 存储成功；GitHub 无对应新提交 |
| 版本冲突 | 拒绝旧版本更新和删除 |
| 保存复杂 MDX | 保持未知特殊语法与文章正文 |
| 手动导出、导入 | 文件可保存、可恢复；同名拒绝覆盖 |
| 私人草稿发布 | 明确确认；无密码/未知元信息；保留私人稿备份 |
| 旧 GitHub 草稿 | 不自动删除、不自动隐藏公开历史 |

**警告**：这套流程仍需要后续接入更强的备份与原子版本控制，不能对敏感资料做完全保密的承诺。
